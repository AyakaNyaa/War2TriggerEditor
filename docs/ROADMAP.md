Статус: план согласован; реализация начата. Прогресс — в STATUS.md.
Оценки в рабочих человеко-днях, без ожидания внешних материалов/ответов.
Дни не равны календарному сроку работы автоматизированного помощника.

## Что уже сделано на этапе согласования

- Изучены инструкция и состав архива, сохранены исходные данные и SHA-256.
- Извлечены ключевые GML-скрипты, проверены секции четырёх карт.
- Сопоставлены четыре PUD/W2TR, исследованы записи имён десяти W2TR.
- Зафиксированы расхождения маркеров, описаний команд и кодировок.
- Подготовлены архитектура, API-сценарии, границы MVP и этот план.

Это не готовая программа и не проверенная реализация форматов.

## Подробные контрольные точки

### 1. Спецификация и каркас

Результат: Cargo workspace, React/TypeScript, минимальное окно,
API health/version и однозначная схема разрешённых зависимостей.
Контракт DTO → OpenAPI → TypeScript проверяется сборкой.
Оболочка запускает и закрывает локальный API; session/Origin-проверки работают.

Первая техническая проверка после одобрения — соблюдение лимита 500 строк
для всех файлов проекта, включая Cargo.lock и frontend lock-файл,
при штатной сборке и обновлении зависимостей. Исключения запрещены пользователем.
До результата этой проверки выбранный набор зависимостей предварительный.
При несовместимости подготовить скорректированный вариант проекта;
не обходить ограничение и не продолжать реализацию с нарушением.

Для команд: таблица длины, аргументов, подкоманд, условий и повторов;
по каждой спорной команде — источник и ограничение экспорта.
Обязательная полнота — все команды в поставленных примерах.
Дополнительные команды реализуются по подтверждённой спецификации,
необъяснённые остаются непрозрачными с диагностикой.

### 2. Форматы

No-op roundtrip: сравнение всех байтов четырёх PUD и десяти W2TR.
После изменения известного поля: меняется только заявленная область,
прочие секции, порядок, имена, хвосты и неизвестные данные сохраняются.
Простое копирование original bytes без проверки редактирования недостаточно.

Негативные случаи: обрезанные заголовки, ложные длины, marker в строке,
нет окончания, FE ED, лишний/повторный OILM, неизвестная команда/подкоманда,
дубликаты имён, неподдерживаемая кодировка и переполнение OILM.
Примеры FE ED в начальных тестах искусственные, не выдаются за реальные карты.
Property-based проверки и fuzzing — для двоичных парсеров и сериализаторов.

### 3. Центральный API и сохранение

Сценарии: открыть → посмотреть → изменить → проверить → preview → сохранить.
Тесты проверяют expectedRevision, смену файла на диске, превышение размера,
ошибку создания бэкапа, отказ записи, сбой между сохранениями PUD/W2TR.
Проверить восстановление при прерывании до/после замены исходника.
Undo/redo не смешивать с восстановлением исходных файлов из бэкапа.

Сохранение только через центр. UI, CLI и будущий AI используют один сценарий.
Неизвестные данные допускают просмотр и сохранение оригинала,
но изменения с неподтверждёнными границами/семантикой блокируются.

### 4. Интерфейс

Минимальный набор: открыть карту и W2TR, добавить известную команду,
изменить аргументы, порядок/условия, дублировать, удалить, отменить, проверить.
Отображать размер программы и вместимость OILM, понятные ошибки,
отсутствие имён при экспорте только в PUD, место и результат бэкапа.

RU/EN, клавиатура, высокая плотность пикселей, изменение размеров окна,
сохранение ширины панелей. API остаётся источником состояния документа;
React хранит несохранённый ввод форм и состояние представления.

### 5. Проверка в War2Combat

До приёмки фиксируются версия игры и War2Mod, способ установки и запуска.
Для четырёх карт: исходный сценарий, no-op экспорт, контролируемая правка,
загрузка в игре, проверка ожидаемого эффекта и отсутствия регрессии.
Для шести ex-файлов: выбрать/создать совместимую карту-контейнер,
загрузить триггеры, проверить сценарии из tr/ex/read.txt.

Автотесты не подменяют проверку игры. Если игровая среда недоступна,
сборка получает статус «нужна игровая приёмка», а MVP не объявляется готовым.
Результаты приёмки фиксируются по версии приложения и хешам выходных файлов.

не включён в эту оценку. В MVP карта нужна как контейнер и контекст триггеров.

## Итоговые критерии готовности MVP

- Все 14 входных примеров покрыты проверками форматов.
- Все используемые в них команды поддержаны или явно ограничены;
  для полноценной приёмки сценариев нужны их редактируемые известные команды.
- Пользователь создаёт и меняет триггеры через формы.
- Файлы без правок побайтно совпадают с исходниками.
- При правках отчёт подтверждает сохранение незатронутых данных.
- Бэкап обязателен, ошибки записи не скрываются, восстановление проверено.
- Есть рабочая Windows-сборка, RU/EN и масштабируемый интерфейс WC2.
- Есть инструкция с примерами и предварительная спецификация форматов.
- Пройдена игровая приёмка на зафиксированной версии War2Combat/War2Mod.
- Архитектурная звезда, API-границы и лимит 500 строк проверяются автоматически.

## Решение пользователя

Предлагается согласовать архитектуру из ARCHITECTURE.md,
границы MVP и последовательность этапов 1–5.
После одобрения начинаем этап 1; расширения 6–9 остаются отдельными этапами.
Для игровой приёмки потребуется точная сборка War2Combat/War2Mod
и доступ к запускаемой игре. На этапе планирования это не блокирует работу.
