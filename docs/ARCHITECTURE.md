# Предлагаемая архитектура

Статус: согласовано; реализация идёт по этапам. Стек пользователя: Rust + React.

## Общий принцип

Одна устанавливаемая программа, модульная архитектура в одном процессе.
Rust workspace. Центральный крейт app-api владеет сеансами редактирования,
историей операций и порядком вызовов. Функциональные крейты — лучи звезды.

React и CLI обращаются только к HTTP API `/api/v1`.
Между Rust-крейтами данные передаются через типизированные публичные API
(traits и DTO), с вызовами только из центра к функциональным крейтам.
Внутренние вызовы не требуют HTTP между крейтами одного процесса.
Функциональные крейты друг друга не вызывают и друг от друга не зависят.

contracts содержит только общие контракты и типы, без бизнес-логики.
Это общая зависимость компиляции, не второй центр управления.
Оболочка связывает реализации при старте; её код не управляет документами.
Вызовы обратно в центр, service locator и общая изменяемая база запрещены.

## Состав workspace

| Крейт / приложение | Ответственность |
|---|---|
| contracts | DTO, коды ошибок, интерфейсы функциональных API, версии контрактов |
| app-api | Центральные сценарии, сеансы, ревизии, undo/redo, HTTP, события |
| format-pud | Чтение секций, сохранение исходных байтов, план патча OILM |
| format-w2tr | Оболочка W2TR, варианты окончаний, записи имён, неизвестные байты |
| trigger-engine | Модель команд, каталог, декодирование/сборка, валидация |
| storage | Открытие, хеши, бэкапы, запись, восстановление, настройки |
| assistant | Позже: API провайдера AI, контекст, предложение правок |
| desktop | Rust/Tauri: окно, запуск центра, завершение процесса |
| cli | Клиент того же HTTP API для inspect/validate/roundtrip |
| frontend | React/TypeScript: компоненты, локализация, представление состояния |

Сеанс хранит исходный снимок, изменяемую модель и журнал правок.
Raw-данные формата не заменяются нормализованной доменной моделью.
Изменённые участки отмечаются явно; неизменённые сериализуются из оригинала.
Форматы возвращают результат и диагностику; запись выполняет только storage.

Центр вызывает format-pud/format-w2tr, получает байты программы,
передаёт их trigger-engine и возвращает DTO интерфейсу.
Сохранение проходит обратный путь через центр и завершается в storage.
Таким образом, format-pud не импортирует trigger-engine или format-w2tr.

## Технологии

Основной вариант: React + TypeScript + Vite; Rust + Tokio + Axum;
serde для обмена, utoipa для OpenAPI, tracing для диагностики.
OpenAPI → генерируемый TypeScript-клиент, общие DTO не переписывать вручную.
Версии и зависимости фиксировать после пробной сборки, через lock-файлы.

Tauri 2 используется для Windows-окна и упаковки.
Весь обмен данными редактора идёт через локальный API,
не добавлять параллельные команды Tauri для чтения файлов или триггеров.
Диалог открытия инициируется запросом API, выполняется Rust-стороной.
React не получает прямой доступ к файловой системе, секретам или форматам.

Альтернатива: тот же Rust API + React в обычном браузере,
без Tauri на первом этапе. Меньше работы с оболочкой, но запуск и управление
локальным процессом менее удобны для конечного пользователя.
Рекомендован вариант с окном Tauri; дополнительный HTTP-слой выбран
ради единого явного API для UI, CLI и проверок.

API слушает только loopback на выделенном при старте порту.
Сессия авторизована; чужие Origin отклоняются, операции изменения защищены
от межсайтовых запросов. Одного CORS для защиты недостаточно.
UI и API предпочтительно обслуживать из одного origin.
Проверка запуска, авторизации и закрытия локального сервера входит в первый этап.

Официальные справочники:
- [Tauri 2: назначение и поддержка frontend-фреймворков](https://v2.tauri.app/start/).
- [Axum: HTTP-маршрутизация и обработчики](https://docs.rs/axum/latest/axum/).
- [utoipa: генерация OpenAPI](https://docs.rs/utoipa/latest/utoipa/).

## Предлагаемые API-сценарии

| Метод и ресурс | Результат |
|---|---|
| POST /api/v1/documents/open | Сеанс, ревизия, тип, диагностика |
| GET /api/v1/documents/{id} | Снимок документа и состояние сохранения |
| GET /api/v1/catalog | Команды, поля, ограничения, профили совместимости |
| POST /api/v1/documents/{id}/changes/preview | Проверенный diff без изменения документа |
| POST /api/v1/documents/{id}/changes/apply | Применение к ожидаемой ревизии |
| POST /api/v1/documents/{id}/validate | Ошибки/предупреждения с привязкой к командам |
| POST /api/v1/documents/{id}/save-preview | План записи, размер OILM, изменяемые области |
| POST /api/v1/documents/{id}/save | Бэкап, безопасная запись, новая ревизия |
| POST /api/v1/documents/{id}/undo или redo | История текущего сеанса |
| GET /api/v1/documents/{id}/backups | Доступные точки восстановления |
| POST /api/v1/documents/{id}/restore | Восстановление с защитой текущего состояния |
| GET /api/v1/events | SSE: прогресс, ревизии, диагностика, позднее поток AI |

Заголовки/DTO фиксируют expectedRevision; несовпадение даёт конфликт.
Коды ошибок стабильны, отображаемый текст берётся из локализации.
Сохранение работает с выбранным через API файловым дескриптором/идентификатором,
а не принимает произвольный путь из любого внешнего запроса.
CLI import/export при необходимости передаёт файлы через этот же API.

События SSE — канал уведомлений центра, не шина обмена между лучами.
AI возвращает proposal_id и структурированный набор изменений;
его результат проходит обычные preview/validate/apply/save.

## Сохранность

При открытии сохраняются original bytes и исходный хеш файла.
Без правок результат должен быть побайтно идентичен входу.
При изменении триггера сохраняются прочие секции PUD, их порядок,
неизвестные поля W2TR и незатронутые данные OILM.

Сначала проверка модели, размера и профиля совместимости, затем план записи.
Непонятная структура не должна автоматически исправляться или нормализоваться.
Если новая программа занимает прежний непрозрачный хвост OILM,
план показывает диапазон замены; при неоднозначной семантике запись блокируется.
Автоматическое расширение OILM и изменение размеров карты в MVP исключены.

Последовательность записи:
1. Заблокировать конфликтующие операции, сверить ревизию и хеш на диске.
2. Создать и проверить бэкап исходного файла; при ошибке прекратить запись.
3. Записать временный файл на том же томе, сбросить данные на диск.
4. Повторно прочитать, проверить формат и ожидаемый diff/хеш результата.
5. Проверить конфликт перед заменой, применить подходящую для Windows замену.
6. Проверить конечный файл, зафиксировать результат и путь восстановления.

Протокол восстановления учитывает прерывание на каждом шаге.
Автосохранение хранит отдельный снимок сеанса, не перезаписывает игровую карту.
Экспорт PUD+W2TR требует журнала: замена двух файлов не является одной
атомарной операцией; сбой должен оставлять понятное восстановимое состояние.
При ошибке второго файла нельзя показывать общий статус «сохранено».

## UI и функциональные границы

Слева список триггеров, в центре последовательность условий и действий,
справа поля выбранной команды; снизу диагностика и размер программы/OILM.
Поддержать поиск, добавление, копирование, удаление, перемещение и undo/redo.
Основные сценарии доступны формами без необходимости писать код.

Стиль WarCraft 2: камень, дерево, металл, читаемая типографика,
без WC3/WoW. Высокая плотность пикселей и увеличение шрифта не ломают раскладку.
MVP: панели меняют размеры и сохраняют раскладку; свободный docking позже.
Карта в MVP — контекст и сведения о секциях; полный редактор ландшафта позже.

i18n: русский/английский, стабильные ключи; fallback English → Russian.
Переключатель показывает название языка; флажок допустим как дополнение.
Остальные девять языков добавляются каталогами без изменения логики.
Бэкенд возвращает коды/параметры, а не вшитые пользовательские сообщения.

Ручной язык позднее компилируется в ту же модель команд, что и формы.
Не предлагать выполнение произвольного JavaScript/Rust или выдуманный язык игры.
AI опционален, сеть включается явно, ключи остаются на Rust-стороне.

## Проверяемые ограничения

- Любой новый текстовый файл, включая тесты, стили, переводы и документацию:
  максимум 500 физических строк; ориентир 150–300 для исходного кода.
- Большие каталоги, схемы и генерируемые клиенты разбивать на файлы.
  Исключений для lock-файлов нет: пользователь их явно отклонил.
  До фиксации зависимостей проверить допустимый формат lock-файлов
  и поведение штатных инструментов при сборке и обновлении.
  Компактное представление допустимо только при корректном чтении инструментами
  и сохранении полноценной фиксации зависимостей; работоспособность не установлена.
  Не обходить лимит архивами, отказом от lock-файла или невалидным разбиением.
  Если ограничение несовместимо с выбранными зависимостями, пересмотреть состав
  и вынести конкретный вариант изменения проекта на согласование.
- Только неизменённые внешние оригиналы аудита (LANG, triggers.txt, GMK, EXE)
  остаются в исходном виде и не считаются новыми файлами реализации.
- Проверка длины файлов и разрешённых зависимостей в CI.
- Cargo: функциональные крейты зависят только от contracts и внешних библиотек;
  app-api организует вызовы; desktop связывает реализации.
- React features не вызывают друг друга: общий API-клиент и композиция в app.
- Сетевые обращения frontend сосредоточены в API-клиенте.
- Форматный код и запись файлов в React запрещены.
- fmt, clippy, проверка TypeScript, meaningful unit/integration/E2E проверки.
